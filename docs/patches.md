# Code patches

Seven patches go beyond text, font and tables: two routines generated by
`ga3.patches` and five assembled from `assets/patches/*.s`. All of them are
`patch` segments in `rom_map.yml`: they own a slot carved out of verified free
space, and they change a few bytes of the game's code elsewhere, each checked
against what the base ROM holds there before anything is written.

| Patch          | What it does                                                                                      | Kind                                                                          |
|----------------|---------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------|
| `menu_version` | `V X.YY.ZZZ` in the middle of the main menu's bottom bar                                          | routine in `ga3.patches`                                                      |
| `menu_items`   | main-menu items 8 characters wide (`1 ИГРОК / 2 ИГРОКА / ДУЭЛЬ / ОПЦИИ`)                          | routine in `ga3.patches`                                                      |
| `kill_counter` | enemies killed by each player, next to their HUD                                                  | assembled from `assets/patches/kill_counter.s`                                |
| `hero_panel`   | the hero stats panel on the character select                                                      | assembled from `assets/patches/hero_panel.s`, data from `data/hero_panel.yml` |
| `difficulty`   | a third difficulty, «ЖЕСТЬ»: the hard enemy set, every ordinary enemy twice                       | assembled from `assets/patches/difficulty.s`, names in `text/difficulty.txt`  |
| `options`      | new options items: БАНКИ МАГИИ (starting magic potions, 0–6), 100 ВРАГОВ (a life every 100 kills) | assembled from `assets/patches/options.s`, labels in `text/options.txt`       |
| `menus`        | the title, the menus and the character select in the README banner's style                        | assembled from `assets/patches/menus.s`, art in `gfx/screens/*.png`           |

Slots (all carved out of verified free space): `menu_version` `0116B6` (0x40),
`menu_items` `0116F6` (0x20), `kill_counter` `011716–0117FF`, `05AEAA` (0x124),
`05B30A` (0x120) and `104940` (0xC0 bonus), `hero_panel` `100000` (0x2000), `difficulty` `102000`
(0x20 names, 0x60 menu, 0x200 spawn; 0x300 place at `102400`, 0x60 drop at `102700`), `options`
`104920` (0x20 labels) and `104A00` (0x200 menu), `menus` `102760` (0x1A0 code, 0x20 text, 0x2000 art);
`102280–1023FF` (the options patch's old slots) and `104C00–1FFFFF` are free.

After a build the pipeline checks that no later segment overwrote a patch's
slot or edits (a text record covering code did exactly that once).

## Assembled patches

A patch written in 68000 assembly lives in `assets/patches/NAME.s` and is
defined once under the top-level `patches:` key of `rom_map.yml`:

```yaml
patches:
  kill_counter:
    source: patches/kill_counter.s
    symbols: { HP: 0x142, P1: 0xC7A4, ... }          # every address the source uses
    hooks:                                           # per section: [address, base bytes, label]
      count: [[0x000E04, "93 28 01 42 6A 04", melee_a0], ...]
    glyphs: { section: tiles, art: gfx/font/font.txt, chars: "0123456789 ", ink: 0x06, bg: 0x0C }
segments:
  - { name: kill_counter_count, start: 0x011716, end: 0x011800, type: patch, fill: 0xFF,
      patch: kill_counter, section: count }
```

Each `section NAME` of the source is placed at the start of the segment with
that `section:`; a hook replaces the six bytes it names with `jmp label.l`.
`strings: { section, path, label }` puts the records of a strings file (the
usual `OFFSET:LENGTH | text`, offsets inside that section's slot, in order from
its start) at `label`, each padded with spaces to its length; `ga3 text
verify/lint/preview` check the file like any other.
`panel: { section, art, data, vram, max_tiles }` (`hero_panel`) renders the
hero panel from the font art and `data` and appends its tiles and tilemaps to
`section`; the build refuses more than `max_tiles` tiles at VRAM `vram`.
`pointers: { SECTION: [[address, base bytes, value], ...] }` points the game's
own code at new data without a hook: the 1, 2 or 4 bytes named (the long of a
`lea abs.l`, an immediate, an entry of a table) become `value`, a label, a
symbol or a number with an optional `+n` / `-n`, checked against the base ROM
like a hook. `art: { section, planes, sprites, palettes, raw }` builds data
from indexed PNGs (`ga3.screen`): `planes` share their distinct 8 × 8 cells in one
Nemesis block and give each file an Enigma map (`ga3.enigma`, the game's own
variant), `sprites` cut a PNG into sprite pieces, `palettes` take a PNG's first
colours as CRAM words and `raw` keeps plain tiles; each block defines `LABEL_COUNT`, each palette
`LABEL_COLOURS` for the source.
The source holds no address of its own. `ga3.m68k` assembles it: a two-pass
assembler for the instructions and addressing modes these patches use, Motorola
syntax, local `.labels`, `dc.b`/`dc.w`/`even`/`section`. Every supported form
is checked by disassembling the output with Capstone (`tests/test_m68k.py`).

## Kill counter

**Counting.** Hit points are a byte at `+0x142` of each object (slots `0x160`
apart; player 1 at `FFC7A4`, player 2 at `FFC904`, enemies from `FFCA64`). Three
places take hit points away and now jump to the patch:

| Hook     | Victim                    | Attacker                                                 |
|----------|---------------------------|----------------------------------------------------------|
| `000E04` | `a0`                      | `a1` (hits)                                              |
| `000E74` | `a1`                      | `a0` (hits)                                              |
| `00F8BC` | `a0`                      | the caster in `$DC4E`: 0 player 1, 1 player 2 (magic)    |
| `00C7F8` | `a0` (object being freed) | the mark: counts an enemy that fell after a player's hit |

Each subtracts as before — and decides death as the game does: the game's
`bpl` clears HP when the result has bit 7 set; the patch uses `bhi` (HP was
above the damage, unsigned), which agrees for every HP the game allows
(0–`0x7F`) and every damage up to `0x80`. (An earlier `bgt` read an overflow,
HP 75 hit for 128, as a living hero with HP 203.) Each also marks the enemy
with the player who hit it (a
byte at `+0x15D` of the object, which the game itself never writes and clears
with the object). The kill goes to the marked player, up to 999, in their word
at `FFC3E0` (player 1) / `FFC3E2` (player 2):

- when the enemy's hit points run out (the three hooks above), or
- when the enemy's object is freed while it still has hit points: it fell off
  the stage after a player's hit (hook on the object clear routine `00C7F8`;
  seen on stage 5A, where an enemy knocked off a ledge is freed with HP left).

An enemy no player hit counts for nobody, also when it falls by itself. An
enemy that leaves the screen alive after a player's hit would count as well;
none was seen doing that on the 13 stages. The counters live in Work RAM the
game never writes after boot (watched over the stages); choosing a game mode in
the main menu (`014FF6`) clears them, so they carry over from stage to stage.

**Display.** Before the game waits for VBlank (`00F006`) the patch looks for
the third HUD block of each player present (tiles `33E` / `36A`, 4 x 3 cells)
among the first 8 sprites of the sprite list (`FFE5CA`, DMA'd to the SAT every
frame) and appends a 3 x 1 sprite just right of the magic boxes: three digits
for each player, right-aligned with blanks for missing leading digits
(`  7`, ` 42`, `999`). The list is
never walked: the game adds sprites in order (sprite n links to n+1) and keeps
their number in `FFEE70`, which its own end-of-list code (`000044`) uses too.
A duel has no enemies to count, so there the counters are not drawn at all:
the game mode (`FFF176`) is 2 for a duel against the computer and 3 once
player 2 joins it, against 0 and 1 for the one- and two-player games.
The three digit tiles per player (`6F8–6FA` for player 1, `6FB–6FD` for
player 2, at VRAM `DF00`) are uploaded when the number differs from the one
they hold (words `FFC3E4` / `FFC3E6`, set to `FFFF` whenever the HUD is not
shown, so they are uploaded again when it comes back), and every 256 frames
anyway (`TICK`, byte `FFC3EA`), so that nothing written over them stays for
long. The digits are the dialogue font's own glyphs, packed to 1 bit a pixel at
build time, drawn in palette 0's white on blue like a dialogue box.
`D000–DFFF` is the window table, unused in play (window off), so the game keeps
sprite art there: objects' animation frames are DMA'd (`010990`) into
`D700–DEFF` on stages 2 and 3A, among others. The tiles were at `D700` first,
and there such a frame replaced the digits by pieces of the object's art (and
the counter's uploads spoiled the object) until the number next changed: the
"wrong number" and the artifacts. `DF00–DFFF` is written by nobody in play on
the 13 stages (450 bot rounds each, every VRAM write watched): only by the
counter and by the clear at `0122D6` between stages, after which the HUD comes
back and the tiles are uploaded again.

A counter is drawn only once its HUD's art is in VRAM: the patch reads back the
first word of each of the player's three HUD blocks (every block starts with a
non-zero border row). A spell clears the HUD tiles, and when it ends the game
puts the HUD sprites back 6-12 frames before it has reloaded their art, block
by block; a stage start loads the art late in the same way. Without the check
the digits showed alone next to an empty HUD for those frames.

**Checked.** `emu/scenes/kill_counter.txt` (hits), magic kills, a 2-player game
(each player's kills go to their counter), all 13 stages through the level
select (`A A A A START C C C C C C` on the character select), the reset, and
`ga3 lag` on `emu/scenes/stage1_fight.txt`: 233 of 3438 frames lost, the same
as without the patch. A busy 2-player fight on stage 6A, replayed from one
savestate with the same input, loses 64 frames in 1239 against 47 without it.
(The first version walked the whole list and redrew the digits every frame:
297 there, a visible slowdown.) After bot play on all 13 stages with two
players the digit tiles in VRAM match both counters, also for 7, 42, 100, 105
and 999 (`emu/scenes/kill_counter_999.txt`: one player from 998 stops at 999
after live kills; two players show 7 / 105 and 999 / 999). Three digits
(words, two divisions) did not change `ga3 lag`: still 233 of 3438 on
`stage1_fight`, 62 in 1239 on the 6A fight.
The HUD art check was verified on VRAM dumped every frame across a spell and a
stage start of a 2-player game: the digits never show without the HUD art.
The move to `DF00`: on stage 2, where an object's frames are DMA'd to `D700`,
the counter showed «26» and then, for as long as the number stayed, pieces of
that object's art; at `DF00` it shows «26» throughout (same bot, same frames).
In a duel against the computer and against player 2 both HUDs are drawn and
no counter is (`emu/scenes/duel_hud.txt`); switching the mode to a duel and
back in a running 1-player game hides the counter and brings it back with the
right digits, because hiding also clears the record of the digits shown.

## Hero stats panel (`hero_panel`)

On the character select the hero under each player's cursor gets a panel over
the title: name, magic, then health, hit / super, tempo and walking speed, each
with a bar (variant B of the mock-ups). One full-width panel (40 × 8 cells) in a
one-player game, a half panel (20 × 9) per player in a two-player game, none on
the duel select (`MODE` ≥ 2).

**Hook.** The select screen's cursor routine (`0161F0–0162A6`) runs once a frame
for each player's cursor block (`FFF300`, `FFF380`) and stores the cursor at
`016278`; the patch replaces that `move.w d0,$14(a0)` and the `mulu.w #6,d0`
after it, does both, and returns to `016280`.

**Drawing.** `src/ga3/hero_panel.py` renders every panel at build time from the
font art and `data/hero_panel.yml` into palette 0's colours (white 6 on blue 12,
the dialogue font's own; yellow 13 and black 9 for the bars), cuts it into
8 × 8 tiles (64, de-duplicated) and tilemaps per hero. The patch copies the tiles
to VRAM `3C40` (118 free tiles on this screen, never written from boot to the
end of the select) and writes the hero's tilemap into plane A (`C000`) over the
title. It draws only when the hero changed, the tiles are not in VRAM (the first
word of tile 0) or plane A no longer holds the panel's corner, so the panel
comes back when the game redraws the screen; interrupts are off while it talks
to the VDP. `SHOWN` (`FFC3E8`, one byte a player) is in the RAM range the game
never writes.

**Numbers.** The build takes them from the game's own tables, the files
`data/hero_panel.yml` names under `sources` (`src/ga3/hero_panel.py`,
`resolve`): hp from `hp_table` (`slot_0`, where every hero starts; the bar's
full length is `slot_3`), hit and super from the constants `KEY_hit` /
`KEY_super` of `data/gameplay.yml` (the first combo hit and the launch), speed
from `walk_speed` (`KEY_x`, 8.8 pixels a frame, shown as pixels a second), the
bars' maxima from the strongest and the fastest hero; `KEY` is each hero's
`key` (`kain` …). `ga3 balance set kain_super 20` therefore changes both the
game and the panel. Tempo (seconds between combo hits) is a measurement and
stays in `hero_panel.yml` with the names and labels. `tests/test_hero_panel.py`
checks the derived numbers against the ROM's tables.

**Checked.** `emu/scenes/hero_select_stats.txt`: the four heroes alone, two
pairs with two players, the duel without a panel; the stage that follows starts
clean; `ga3 lag` on `stage1_fight` unchanged (233 of 3438).

## Difficulty «ЖЕСТЬ» (`difficulty`)

OPTIONS → СЛОЖНОСТЬ has three values: ОБЫЧНО, ТРУДНО and **ЖЕСТЬ**: the
enemies of ТРУДНО, and every ordinary enemy comes twice. The screen still holds
at most four enemies (four enemy slots, each with its own VRAM area), so the
fights get longer, not more crowded.

**What the game does.** The difficulty is the byte `$FFC726` (0 normal, 1 hard;
kept over a soft reset at `0002CC`). Its only reader in play is the spawn walker
(`00C1BE`): an entry of the stage's spawn data has a level (bits 31..30 of its
second long), and it is skipped when that level is above the difficulty (plus
one while both player objects exist, `$C408` = 3; 0 in the attract demo,
`$C718` bit 0). So ТРУДНО is ОБЫЧНО plus the level-1 entries, nothing else.

**Menu** (`0152E4`, reached by `bsr` with `d1` = −1, 0, +1): the value now wraps
over 0..2 both ways and its name, six characters, comes from
`text/difficulty.txt` (the old strings at `015318` are no longer read).

**Level** (`00C1BE`): the difficulty counts as at most 1, so ЖЕСТЬ spawns
exactly the entries of ТРУДНО.

**Twice.** At ЖЕСТЬ (not in the demo), once a plain entry of an ordinary type
(`10 12 14 16 18 1A 1C 2C 34 36 38`, handler `007954`) got an enemy slot
(`00C1FE`), the entry goes into a queue once more, with the X the game just
gave it. Bosses (`32`, `2E`, `1E`), riders (commands 07/08) and command entries
are never doubled; an enemy a command handler spawned is copied as a plain
enemy. Every frame (`00BDBA`, the spawner's frame routine, not run while magic
plays) the oldest queued entry goes through the game's own spawn routine
(`00C0FE`) as soon as an enemy slot is free and the previous copy came in at
least `GAP_FRAMES` (40) frames ago: one at a time. The game drops an entry that finds no free slot
(`00C1F6`); at ЖЕСТЬ an ordinary one is queued instead, with its copy, so the
copies never cost an original. A queued entry is not tested for its level again
(it passed when it came up; the two-player bonus may have changed since).
While entries wait, the wave is not cleared (`00C66E`) and the stage end does
not see an empty screen (`00C650`): the next wave and the scroll wait for them.
The routine that clears the game state at a stage start (`00E552`) empties the
queue.

**Where a copy comes in** (section `place`, `102400`). A copy comes in later
than its original, often much later, so the original's spot is no good: the
camera has moved on and the spot is behind it, or the original was placed by a
command handler (dropping in from a ledge, from the back of the stage) and the
copy, given only the entry, started inside the floor at depth 0 and fell through
it. So the copy comes in like the game's own edge entries, just past an edge of
the screen (camera + `150` or camera − `10`, the edge nearer to where the
original came in first), on ground at the player's level, and walks in. The
ground comes from the stage's collision boxes, the table the physics step reads
at `002CAC` (`TERRAIN` `02DE5A`: stage `$C778` → part `$C77A` → 64-pixel column
→ a list of offsets to boxes of seven words: X, depth and height as centre and
half size, then a type; `002E8E` lands an object on a box only when it entered
the box by no more than one frame's fall, which is why a spawn inside a box
falls through it). The first column's offset is the size of the column table, so
`floor` reads no column past the end of a stage (stage 10 has 14 columns, X <
896, with the camera at 736). At the player's depth (or else the entry's) a spot
is taken when the highest plain box top under it is at most `UP` (120) above and
`DOWN` (16) below the ground under the player (`+0x74`, written by `002EEE`),
with no box over that ground within `BODY` (64) and no special box (type ≠ 0) at
all; the copy starts two pixels above that ground. Each edge tries a few X
around the edge (`RIGHT_X`, `LEFT_X`, never more than 8 pixels inside the
screen: a seam between two boxes or a pit right at the edge is common), then the
other edge; where neither depth fits (an arena walkable at its edges only nearer
the back), the middle depth of a floor box there. A copy that finds no spot
waits; after `WAIT_FRAMES` (240) frames without one it is dropped, so a wave
never waits for it for ever.

**Potions** (section `drop`, `102700`). A gnome (a thief; the bot met them on
stage 1 and after its cart, where several run through the grass) carries items:
its count `+0x43` is set when it appears (`009BB0`, from `$EF3E` / `$EF3F`) and
its kind `+0x42` (0 potions, 1 and 2 meat). Each player's hit that finds it
carrying drops one (`0098A0–0098C0`): a free item slot (`00BCCA`: `FFD584`, 8 of
`0xB4`), one item moved from `+0x43` to `+0x44`, an object of type `4C` with its
frame `+0x14` set to the kind, spawned where the gnome is (`006DEE`, `d5` = the
new `+0x44` to the item's `+0x8F`, which picks one of nine flights at `0EFAD8`).
The pick-up (`0009E2`) reads the frame: 0 adds a potion (`000A16`, at most 6).
At ЖЕСТЬ (`0098B8`) a potion comes with a second one from no stash, on the
neighbouring flight (1 and 0, 2 and 3 …, 8 and 7) so the two fly apart: the same
hits give twice the potions. Meat stays single; when all eight item slots are
taken the second potion is skipped. Checked with the bot of the copies (stage 1
and the grass after its cart): four hits on gnomes put two potion objects each
in the item slots instead of one, and they flew apart
(`emu/scenes/difficulty_potions.txt`).

The queue (16 entries of 8 bytes, a ring) lives at `FFBF00`: `FFBCC0–FFBFFF` is
written only by the RAM clear at power-on (watched over all 13 stages). Two
places that looked free were not: `FFC480–FFC5FF` is the Nemesis decoder's
table, rebuilt at every decompression, and `FFC600–FFC700` is the stack.
`GAP` and `WAIT` are the bytes `FFBF03` and `FFBF04`.

**Checked.** `emu/scenes/difficulty.txt`: the menu both ways and stage 1 with
four enemies on screen and copies waiting. With a bot (player kept alive) on
stage 1, every ordinary enemy came exactly twice (41 pairs, the boss once); on
the 13 stages through the level select, ЖЕСТЬ finished every stage the same
bot finished on ТРУДНО, and the stages it did not finish stopped the same way
on ТРУДНО. The demo spawns the same enemies at the same frames as without the
patch. ОБЫЧНО and ТРУДНО spawn the same enemies as before.
`emu/scenes/difficulty_copies.txt`: stage 8, a skeleton's copy walking in from
the right edge on the floor. Where the copies come in, checked with the same bot
over the 13 stages (450 rounds each, Work RAM dumped twice a round): copies that
fell more than 40 below the floor they started on, or stayed alive more than 40
pixels off screen for eight dumps, went from 97 of 510 to 21 of 411 (the rest
are steps down to the player's level and enemies the camera left behind); no
copy waited with every enemy slot empty, also in two-player games on four stages
(41–53 copies each, both players walking), and the demo's Work RAM over 9000
frames is the same as without the patch; `ga3 lag` loses no more frames. With
the old placement the bot was stuck on stage 8: two skeleton copies stood inside
the floor (height 825, the floor 953) with HP left, out of reach, and the wave
never ended; now it finishes the stage. Every other stage got as far as before
(stage 7 needs the player at the exit's depth, which the bot reaches only by
chance). Lag on stage 1: 2.5 % of frames lost on ЖЕСТЬ against 1.0 % on ТРУДНО
(more often four enemies at once).

## Options: БАНКИ МАГИИ and 100 ВРАГОВ (`options`)

The options screen gets two items before МЕНЮ: **БАНКИ МАГИИ**, the magic
potions a player gets when they have none, 0–6 (left / right, around both
ways), and **100 ВРАГОВ**, ВЫКЛ / ВКЛ (default ВЫКЛ): an extra life for every
hundred kills, see [the life](#the-life-every-100-kills). Seven items do not
fit the game's spacing, so below КНОПКИ every item is two rows from the next:
МУЗ. `0F`, ЗВУК `11`, БАНКИ МАГИИ `13`, 100 ВРАГОВ `15`, МЕНЮ `18` (the game:
`10`, `13`, —, —, `16`). The label rows are bytes in `text/menu.txt`; the МУЗ.
and ЗВУК values are drawn at the cells in `move.w #$c830,d0` (`0153D4`) and
`move.w #$c9b0,d0` (`015420`), whose operands the patch points at rows `0F` and
`11` (`pointers:`). More items can follow the same way: a label in
`text/options.txt`, a row in the cursor's table, an index in `item`; the label
font has no capital Й (3 bytes are left after recompression, the cheapest Й
drawn in the free slot `7B` needed 5), hence «100 ВРАГОВ», not «100 УБИЙСТВ».

**What the game does.** The options screen (`0150A8`) draws its labels from
the table at `01512C`, each value through its item routine with `d1` = 0, then
the cursor (`01525A`: `$F160` 0..4, rows `08 0B 10 13 16` from `0152A8`, column
7 cleared with `01207C`). Left / right (`0152AE`) go through a jump table
(`0152D8`, item 4 = `rts`); a button on item 4 leaves (`01543C`). The potions
come from `00E476`: when a player's count (`+0x140`) is 0 it writes the
constant `potions` (`move.b #N,$140(a0)` at `00E47C`) — at the start, after a
death and after a continue.

**Hooks.** `0150FE` (screen entry): both labels and values. `01525A`: the
cursor over seven rows (the column cleared down to row `19`). `0152C8`: items
4 and 5 are the new ones, item 6 (МЕНЮ) does nothing, items 0–3 go through the
game's table. `01543C`: МЕНЮ is item 6. `00E476`: the count the setting gives instead
of the constant; in the attract demo it stays 1, the base game's count, which
the demo's recorded input expects.

**The value** lives in `$FFC729`: the game keeps the long at `$C726` over a soft
reset (`0002CC` / `0002E8`; `C726` difficulty, `C727` buttons, `C728` used in
play) and clears it at power-on, and nothing else writes `C729` (watched from
boot through the options, stage 1, deaths and game over). Bits 0–6 hold the
count minus the default, bit 7 is 100 ВРАГОВ, so power-on gives the default
and ВЫКЛ, and the default is still the
constant `potions` (`ga3 balance set potions N`), read at run time from the
operand of the bypassed instruction (`00E47F`). The default is now 0.

**Checked.** `emu/scenes/options_potions.txt`: the seven items, the value around
both ways, the cursor around past 100 ВРАГОВ and МЕНЮ, C on МЕНЮ back to the main menu, stage 1
with six potions (three full jars). Set to 3, a player emptied to 0 gets 3
again after a death. Work RAM over the first 6000 frames from power-on (title,
attract demo) is the same as without the patch, byte for byte, but for `C729`.

### The life every 100 kills

**What the game does.** Every frame `0103B4` runs a HUD state of 16 bytes
for each player present (`$DC24` player 1, `$DC34` player 2). When the
prisoners freed (`+0x13E`) reach 5 (`0103F2`), it subtracts 5, sets the state
to blink (`+0xC` 1, `+0xD` `0F` frames, `+0xE` 5 toggles), shows all five
prisoner icons (`+0x138`), adds a life (`addq.b #1,$13c(a1)` at `010416`) and
queues sound `DF` (`00E4B2`, which keeps every register). Each toggle
(`0103C0`) flips the icons and plays `DF` again; at the end (`0103E2`) the
state is cleared, and the next frame copies the real count back from
`+0x13E` (`0103EC`).

**The patch.** The kill counter's `kill` (it moved to the new slot `104940`,
section `bonus`, called with `jsr` from the four hit and free hooks) calls
`bonus` after a counter goes up. With bit 7 of `$C729` set and no demo
playing (`$C718` bit 0), a counter at a multiple of 100 gives its player a
life and starts the same blink and sound, so the player sees what they see for
five prisoners; the prisoner count itself is not touched. A player with 9
lives (all the HUD's one digit shows; constant `lives`, `max_hud`) gets none.
The counters stop at 999, so a game gives at most nine such lives; they are
not cleared on a continue, so the kills before it count towards the next
hundred. A duel has no counters, so no lives either.

**Checked.** `emu/scenes/options_extra_life.txt` (player 1, kill bot): ВКЛ on
the options screen; the counter at 99, the next kill: lives 2 → 3, written by
the patch (watch `FFC8E0`: `pc=1049AA`), the five icons on, off, on and gone;

## Menus in the banner's style (`menus`)

The title, the main menu, the options, the character select and the ending's
THE END are redrawn in the style of `docs/branding/banner.svg`: a navy sky with
checker dither and drifting cloud strips, the blocky gold logo with a black
outline, a gold cursor, and a black bottom bar under a gold line with СЕГА,
НАЖМИ СТАРТ (blinking) and 2О26 NЕWGАМЕ. The art is drawn from the SVG by
`ga3 banner-art` into `assets/gfx/screens/*.png` (indexed, one palette line each;
edit them or the generator) and turned into tiles, maps and palettes at build
time. Most of the patch is `pointers:`: the game's own loaders get new data.

**What the game does.** The title's setup (`0156B0`) loads five Nemesis blocks
from the list at `0158B4` (tile word + source long each): the logo `1B780` at
tile `080`, the sky `1D0D6` at `0F8`, two blocks at `149` / `168` (the sword
and the axe that fall into the logo) and "III" `1D6D2` at `17D`. Its maps are
Enigma (decoder `01252C`, the base attribute in `d0`): the logo `0EB490` as
38 × 6 cells at plane A `C104`, the sky `0EB5E8` as 32 × 28 cells written twice
to plane B. Palettes sit in ROM too: the logo's `0EB200` (12 words, palette 1),
the sky's `0EB278` (5 words, palette 0, halved by `014D40` after the white
flash), the text's `0EB2A2`. "III" is an object (`01587C`, mapping `0EB7DE`).
The logo map has a grid the game relies on: each letter in its own 4-cell
column from plane column 2 — the title slides it in four columns at a time
(per-column V-scroll), the intro's 2× scroller (`0155EC`) doubles 38 × 6 cells and
120 tiles, and the ending copies E, E, N, D out of it (`01742E`) next to a "TH"
built from the same tiles (`0EB51C`).

**The art keeps that grid.** The banner's letters (a 5 × 7 bitmap font, each
pixel a 2 × 2 gold block, outlined by a ring plus a drop shadow) go one to a
column; T and H for the ending are drawn by the same rule. The logo and TH
share one block of at most 120 tiles (89 now), without mirrored cells, which the
scaler could not draw. "III" is a 10 × 6-cell sprite of its own (60 tiles, six
pieces, `III_SPRITE` in the source). The sky (92 tiles) moves to tile `1C0`
(VRAM `3800–4380`, unused on the title); the select screen's sky, 40 × 28 cells
in 52 tiles, goes to tile `4EF` (VRAM `9DE0–A640`, never written on the one-
and two-player select).
